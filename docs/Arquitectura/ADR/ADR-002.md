# ADR-002 — Organización de Módulos

**Fecha:** 2026-07-14

## Decisión tomada

`app/` deja de contener lógica de negocio. A partir de ahora `app/` solo puede contener:

- Páginas (`page.tsx`)
- Layouts (`layout.tsx`)
- Route handlers (`route.ts`)
- `loading.tsx`
- `error.tsx`

Toda la lógica de negocio vive en `modules/`. Por ejemplo, `modules/sales`, no `app/sales`.

## Motivo

Auditoría de arquitectura detectó lógica repartida entre `app/` y `modules/` para los mismos dominios (ej. `sales`, `inventory`). Páginas como `app/(dashboard)/sales/quotes/new/page.tsx` (333 líneas) y `app/(dashboard)/sales/invoices/[id]/page.tsx` (536 líneas) tienen lógica de negocio embebida en vez de delegarla a `modules/sales`. Esto dificulta mantenimiento, testing y reutilización a medida que GestForce crece como SaaS.

## Reglas derivadas

### 1. Estructura interna de cada módulo

Cada módulo (`modules/<dominio>`) debe tener esta estructura, aunque algunas carpetas empiecen vacías:

```
modules/sales/
  components/
  hooks/
  services/
  types/
  schemas/
  actions/
  utils/
  constants/
```

Razón: dentro de un año, módulos como Ventas tendrán cientos de archivos. Sin esta separación, todo se mezcla en un puñado de archivos gigantes.

### 2. Servicios: eliminar carpeta global `services/` por dominio

En vez de una carpeta global `src/services/` acumulando un archivo por dominio (`sales.ts`, `inventory.ts`, `customers.ts`, ...), cada módulo maneja sus propios servicios:

```
modules/sales/services/
  sales.service.ts
  quote.service.ts
  invoice.service.ts
```

`src/services/` global queda reservado **solo** para lo verdaderamente transversal: correo, pasarelas de pago. (Los archivos actuales `payment-provider.ts`, `bold.ts`, `email.ts`, `subscription-checkout.ts` en `src/services/` califican como transversales y se quedan ahí.)

### 3. Hooks: dos niveles

```
src/hooks/          -> genéricos, sin dominio (useDarkMode, useDebounce, useMediaQuery)
modules/sales/hooks/ -> específicos del módulo
```

### 4. Types: dos niveles

```
src/types/          -> database.ts, common.ts, api.ts
modules/sales/types/ -> tipos propios del módulo
```

### 5. Config

`src/config/` se revisa aparte; pendiente de decidir si se divide, según su contenido actual.

## Lo que NO se toca

- `components/ui`
- `store`
- `app/api`
- `(superadmin)`

## Impacto

- Cada módulo se vuelve casi independiente y más fácil de mantener.
- Separación clara entre administración del sistema (`subscription`, `companies`, `users`, `modules`, `payment`) y operación diaria de cada empresa — decisión clave para un SaaS multi-tenant, ya reflejada en la estructura actual de `modules/`.

## Hallazgo relacionado (fuera de alcance de este ADR)

Existen dos páginas de inventario activas: `app/(dashboard)/inventory/page.tsx` y `app/(dashboard)/inventario/page.tsx`. Requiere decisión aparte sobre cuál es la vigente antes de migrar ese módulo.
